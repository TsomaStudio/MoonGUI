# MoonGUI — архитектурная спецификация (этап 1)

*Редакция 0.2 · решения владельца в разделе 16 приоритетнее разделов 1–15 · 3 ноября 2026 · исходный код на этом этапе не пишется*

## 0. Резюме

Документ закрывает 14 пунктов задания. Для каждого решения приведены альтернативы, плюсы и минусы, выбор и последствия для долгосрочного развития. Выбор делается по приоритетам проекта в заданном порядке (корректность, производительность, мультиплатформенность, расширяемость, минимальные затраты, удобство API), а не по популярности технологии. Когда приоритеты конфликтуют, побеждает более высокий: например, типизированные handles вместо сырых указателей, потому что корректность важнее нескольких наносекунд.

**Допущения исследования**

- Рабочее имя и префикс публичного API — `mg_` (от MYGUI); см. вопрос Q1 в разделе 15.
- Целевые ОС: Windows 10 22H2 и новее, Linux (Wayland и X11), macOS 12 и новее. Минимальные версии — предложение, подлежит утверждению.
- Числовые цели производительности — гипотезы. Они калибруются по baseline-замерам фаз 0–1 и только после этого становятся обязательными gate'ами (принцип 8: не оптимизировать без измерений).
- Версии, лицензии и статус внешних компонентов нужно перепроверить в ADR перед фиксацией каждой зависимости: документ опирается на знание экосистемы, а не на свежую сверку с первоисточниками.

## 1. Общая архитектура

### 1.1 Базовая модель интерфейса (D-01)

| Модель | Плюсы | Минусы |
| --- | --- | --- |
| Immediate-mode (стиль Dear ImGui) | Минимум состояния, простой API | Пересчёт и перерисовка каждый кадр противоречат цели нулевого CPU в простое; IME, accessibility, анимации и виртуализация реализуются тяжело; идентичность виджетов держится на хэшах |
| Retained-дерево виджетов | Dirty-tracking и damage rects, семантическое дерево для accessibility, виртуализация, кэш раскладки и текста | Больше кода; нужна синхронизация данных приложения и UI; риск «висячих» ссылок |
| Декларативный diff (React/Elm) | Простая прикладная модель | Требует замыканий и аллокаций на каждый кадр; в C неудобен и давит на память |
| Нативные виджеты ОС | Родной вид и поведение | Противоречит цели самостоятельной технологии и единому поведению на трёх ОС |

**Решение:** retained-режим для виджетов; рисование идёт через display list (линейный буфер команд), а для пользовательской графики есть виджет Canvas с immediate-API. Immediate-фасад можно позже добавить отдельным слоем над публичным API, не меняя ядро.

**Последствия:** данные принадлежат приложению, UI — их отражение; для коллекций вводится интерфейс моделей данных; любые изменения виджетов идут через сеттеры, которые выставляют dirty-флаги (стиль, раскладка, рисование, accessibility) и будят планировщик кадров.

### 1.3 Правила зависимостей

1. Зависимости направлены только вниз; циклов нет. Контроль двойной: граф CMake-целей и скрипт `tools/check_layers`, который падает в CI при запрещённом `#include`.
2. Системные заголовки (`windows.h`, X11, Wayland, Cocoa, Metal, D3D) разрешены только в `src/platform/<os>/` и `src/render/backends/<name>/`. Публичные заголовки не включают системные.
3. Заменяемые части (платформа, backend, shaper, провайдер буфера обмена) описываются структурой указателей на функции; реализации выбираются при создании контекста.
4. Layout знает только абстрактный узел (размеры, constraints, дети) и измеряет текст через callback, поэтому тестируется без окон, шрифтов и GPU. Тем же принципом связаны Theme и Widget.
5. Глобального изменяемого состояния нет: всё живёт в `mg_context`. Исключение — thread-local scratch-арены.
6. Для каждой подсистемы существует null/fake-реализация зависимостей для юнит-тестов.
7. Мягкие лимиты (ловит линтер): файл `.c` — до \~1000 строк, функция — до \~100 строк.

### 1.4 Конвенции публичного API (D-03)

**Идентификация объектов.**

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Непрозрачные указатели | Просто, нулевой overhead, типобезопасны отдельными struct-типами | Use-after-free: дерево уничтожает детей вместе с родителем, а приложение держит неучтённые ссылки |
| Целочисленные ID | Сериализуемы, безопасны | Нет типовой безопасности в C |
| Типизированные generation-handles (пара «индекс + поколение» в struct на каждый вид объекта) | Устаревшая ссылка обнаруживается и возвращает ошибку; типобезопасность; компактные пулы; удобно для FFI | Один поиск в таблице на вызов; немного сложнее отладка |

**Решение:** handles в публичном API, сырые указатели внутри ядра. Стоимость вызова пренебрежима, а класс ошибок «обращение к уничтоженному виджету» исключается по построению.

**Остальные соглашения.**

- Именование: функции `mg_<модуль>_<действие>`, типы `mg_<имя>`, макросы `MG_<ИМЯ>`; единый макрос видимости символов.
- Ошибки: все операции возвращают код результата; значения возвращаются через выходные параметры. Ни исключений, ни `longjmp`, ни `errno`. Предусловия публичного API проверяются всегда и дают код ошибки; в debug-сборке дополнительно срабатывает assert. Нехватка памяти возвращается кодом, а не abort (поведение настраивается).
- Создание объектов: через структуры-дескрипторы, где первым полем стоит размер структуры, а нулевая инициализация означает значения по умолчанию. Так API расширяется без поломки ABI.
- Callback-и всегда парой «функция + userdata», с необязательным деструктором userdata.
- Строки: UTF-8, пара «указатель + длина»; библиотека по умолчанию копирует переданные строки. Владение (заимствовано, передано, скопировано) указывается в документации каждой функции.
- Потоки: если не сказано иное, вызовы допустимы только из UI-потока. Потокобезопасны явно помеченные: постановка задачи в очередь UI-потока, счётчики ссылок ресурсов, фоновое декодирование.
- Версионирование: SemVer; до 1.0 API считается нестабильным, но каждая несовместимая правка проходит через deprecation-политику. Статическая сборка по умолчанию, shared — опционально.
- Документация: Doxygen-комментарии для каждого публичного символа; CI проверяет покрытие.

### 1.5 Модель потоков (D-05)

| Модель | Плюсы | Минусы |
| --- | --- | --- |
| Один UI-поток, всё в нём | Простота, отсутствие блокировок, предсказуемость; так устроены нативные тулкиты всех трёх ОС | Тяжёлая отрисовка конкурирует с обработкой ввода |
| UI-поток + отдельный render-поток | Отрисовка не блокирует ввод; лучше загрузка многоядерных CPU | Нужны неизменяемые снимки сцены, синхронизация ресурсов; сложнее отладка |
| Многопоточное дерево виджетов (job system) | Теоретический максимум | Огромная сложность и риски корректности, неоправданные для GUI |

**Решение:** UI-поток владеет деревом виджетов, раскладкой и событиями. Фоновые задачи (декодирование изображений, раскладка больших текстов, ввод-вывод) выполняет пул воркеров и возвращает результат через потокобезопасный post. Display list формируется как неизменяемый снимок в арене кадра, поэтому перенос выполнения backend в отдельный render-поток возможен позже как локальное изменение. До замеров, показывающих такую необходимость, отдельного render-потока нет.

**Последствия:** на macOS и Windows ряд системных вызовов обязан идти из главного потока — это совпадает с моделью. Длительные операции пользователя обязаны уходить в воркеры; для этого API предоставляет примитивы.

### 1.6 Конвейер кадра

```text
Пробуждение --> Events --> Animation tick --> Style --> Layout --> Paint --> Render core --> Backend --> Present
(ОС, таймер,                (если есть        (если    (если     (display  (batching,      (submit)   (если damage
 post из потока)             активные)         dirty)   dirty)    list)     атласы)                    не пуст)
```

Каждая стадия работает только над dirty-подмножеством. Если ни одна стадия не выставила работу, кадр не создаётся и поток спит в блокирующем ожидании ОС; таймеры и vsync-колбэки включены только пока есть активные анимации. Арена кадра сбрасывается в конце кадра, но её память не возвращается ОС сразу (политика сжатия — в разделе 3).

## 2. Графические backend'ы

### 2.1 Критерии оценки

Корректность и одинаковый результат на всех ОС; эффективность на 2D-нагрузке (тысячи прямоугольников, глифы, тени, скругления, clip); надёжность драйверов на массовом железе; число и вес внешних зависимостей; живучесть API (не deprecated); поддержка frame pacing, HiDPI и потери устройства; стоимость сопровождения; наличие программного fallback.

### 2.2 Кандидаты

| Backend | ОС | Плюсы | Минусы | Вердикт |
| --- | --- | --- | --- | --- |
| Software (собственный) | все | Эталон корректности; работает в VM, RDP и CI без GPU; нет зависимости от драйверов; детерминирован | Нагрузка на CPU на 4K и при анимациях; нужна SIMD-оптимизация | Обязателен: эталон и fallback |
| Direct3D 11 (FL 10.0+) | Windows | Зрелый; работает на любом железе, включая старые iGPU; простой API; flip-model swap chain; WARP как программный запасной путь | Только Windows; Microsoft развивает D3D12, но D3D11 стабилен и поддерживается | Основной на Windows |
| Direct3D 12 | Windows | Минимальный overhead | Многословен; для 2D UI выигрыш ничтожен; больше кода и рисков | Отклонён |
| Metal | macOS | Единственный современный нативный API Apple; точный контроль frame pacing через CAMetalLayer | Только Apple | Основной на macOS |
| OpenGL 3.3 core / GLES 3.0 | Linux; запасной на Windows | Самый широкий охват на Linux (Mesa); EGL работает и в Wayland, и в X11; простая модель | На macOS заморожен и deprecated; качество драйверов на Windows неровное; нет явной синхронизации | Основной на Linux |
| Vulkan | Windows, Linux (macOS через MoltenVK) | Современный, явный, предсказуемый | Очень многословный; тяжёлая инициализация; MoltenVK — внешняя зависимость; для 2D избыточен | Отложен; возможен как второй backend на Linux, если замеры покажут пользу |
| WebGPU native (wgpu-native, Dawn) | все | Один API и один язык шейдеров | Тяжёлая зависимость (крупная кодовая база на Rust или C++), десятки МБ, стандарт ещё меняется | Отклонён по критерию зависимостей |
| sokol\_gfx / bgfx | все | Готовые абстракции | sokol: небольшой набор возможностей, ограничивает контроль над батчингом; bgfx: C++ и тяжёлый | Отклонены; sokol\_gfx допустим только для одноразового прототипа |
| Нативные 2D API (Direct2D, CoreGraphics, Skia, Cairo) | по ОС | Готовое качественное рисование контуров и текста | Разный результат на разных ОС; нет контроля над батчингом и кэшами; Skia огромна и на C++; Cairo ориентирован на CPU | Отклонены как основной путь |

### 2.3 Стратегии: как собрать кандидатов (D-06)

| Стратегия | Объём кода backend | Надёжность на целевых ОС | Внешние зависимости | Долгосрочный риск |
| --- | --- | --- | --- | --- |
| A. Один OpenGL везде | 1 backend | Windows: зависит от драйверов, особенно встроенных GPU; macOS: API заморожен и deprecated | Загрузчик GL | Высокий: Apple может убрать OpenGL |
| B. Один Vulkan (MoltenVK на macOS) | 1 backend + слой | Высокая на Windows и Linux; на macOS работает поверх Metal через сторонний слой | Vulkan loader, MoltenVK, шейдерный toolchain | Средний; тяжёлый старт и большой объём кода |
| C. Нативные D3D11 + Metal + OpenGL 3.3 + software | 3 GPU-backend + software | Высокая: на каждой ОС используется основной поддерживаемый путь | Только системные API | Средний: сопровождение 4 реализаций (снижается, см. 2.4) |
| D. WebGPU native | 1 backend | Зависит от качества wgpu/Dawn на каждой платформе | Очень тяжёлая | Высокий: стандарт и API меняются |

**Решение:** стратегия C. Единственная стратегия, где на каждой ОС задействован основной, долгоживущий и не требующий внешних зависимостей путь. Её главный минус (четыре реализации одного интерфейса) мы компенсируем архитектурой из 2.4.

### 2.4 Архитектура: renderer core и узкий интерфейс backend

Рендеринг разделён на два уровня.

**Renderer core (общий код, не знает про API).** Принимает display list, разрешает трансформации и clip, сортирует и склеивает команды в батчи с сохранением порядка рисования, управляет атласами (глифы, иконки, изображения), тесселирует контуры, выделяет offscreen-слои из пула и формирует список батчей.

**Backend (узкий интерфейс, порядка 25–30 операций).** Группы операций:

- поверхность: создать из нативного окна, изменить размер, уничтожить, узнать возраст буфера (для частичной перерисовки);
- кадр: начать кадр, выполнить список батчей, закончить, показать (с damage-областью, если API позволяет);
- ресурсы: текстуры A8, RGBA8, BGRA8, обновление подобласти, offscreen-цели, кольцевой буфер потоковой загрузки вершин и instance-данных;
- сервис: запрос возможностей, чтение пикселей назад (скриншоты и тесты), GPU-таймеры для замеров.

**Типы батчей (около 10):** instanced-прямоугольники со скруглением, рамкой и градиентом; тень и размытие; текстурированный квад (изображения, 9-slice); глифовый квад (A8 и цветной); сетка контура (сплошная или градиент); контур через маску покрытия; начало и конец offscreen-слоя; смена scissor и clip.

**Принципы рисования.** (1) Основные формы (прямоугольники, скруглённые прямоугольники, окружности, линии, тени) считаются аналитически в пиксельном шейдере через signed distance, это 90% UI-рисования. (2) Произвольные контуры тесселируются на CPU с кромкой для сглаживания и кэшируются. (3) Сложные формы и глифы растеризуются общим CPU-растеризатором покрытия в маски, которые загружаются как текстуры. Один растеризатор покрытия обслуживает и software-backend, и маски для GPU, поэтому поведение совпадает.

**Шейдеры.** Около 8 пайплайнов. Пишутся вручную на HLSL (SM 4.0), MSL и GLSL (3.30 и ESSL 3.00). Parity-тест рисует одну и ту же сцену на всех backend и сравнивает с software-эталоном с допуском. Если пайплайнов станет больше \~15, вводим оффлайн-кросскомпиляцию как dev-инструмент (результат хранится в репозитории); это решается отдельным ADR. Шейдерный компилятор не становится зависимостью времени выполнения.

**Выбор и устойчивость.** Backend выбирается при создании окна: предпочтительный GPU-backend, затем software. Принудительный выбор — через API или переменную окружения. Потеря устройства (DEVICE\_REMOVED, сброс GL-контекста) обрабатывается пересозданием: все GPU-ресурсы воспроизводимы из CPU-источников, которые держит менеджер ресурсов.

### 2.5 Последствия

- Четыре реализации одного интерфейса — постоянная цена. Её ограничивают: узкий интерфейс, общий renderer core, software как эталон, parity-тесты на каждом изменении.
- Используем только общий знаменатель возможностей: без compute и geometry shaders. Необязательные возможности (частичный present, buffer age) подключаются через флаги capability.
- Vulkan не закрыт: в интерфейсе нет ничего, что мешает добавить пятый backend. Возвращаемся к вопросу, если замеры покажут проблемы OpenGL на Linux.
- CI ограничен программными/виртуальными GPU: WARP на Windows, llvmpipe на Linux, Metal на macOS-раннере. Реальные GPU проверяются ручной матрицей перед релизами.

## 3. Управление памятью

### 3.1 Требования

Минимум аллокаций и RSS; предсказуемая задержка; безопасность (утечки, use-after-free, переполнения); возможность встраивания (приложение-хозяин может управлять памятью); диагностируемость; без сборщика мусора.

### 3.2 Альтернативы (D-04)

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| Только malloc/free | Просто | Много мелких аллокаций, фрагментация, нет учёта, непредсказуемая задержка |
| Только арены | Очень быстро, нет утечек внутри арены | Виджеты создаются и удаляются независимо, единая арена не годится; риск висячих ссылок после сброса |
| Ref-counting везде | Автоматическое владение | Циклы parent/child; атомарные операции на горячем пути; скрытая стоимость |
| Garbage collector | — | Запрещён требованиями |
| Гибрид по классам времени жизни | Для каждого вида данных дешёвая и безопасная модель | Нужна дисциплина: каждая аллокация явно относится к классу |

**Решение:** гибрид.

### 3.3 Классы времени жизни

| Класс | Аллокатор | Время жизни | Примеры |
| --- | --- | --- | --- |
| Context | Внедряемый аллокатор (по умолчанию malloc) | До уничтожения контекста | Реестр классов виджетов, темы, таблицы |
| Window | Арена окна | До закрытия окна | Список damage, стек overlay, метаданные поверхности |
| Widget | Slab-пул на класс виджета + generation-handles | До уничтожения виджета | Структуры виджетов |
| Resource | Блоки с атомарным счётчиком ссылок | Пока есть ссылки | Изображения, шрифты, атласы |
| Frame | Линейная арена, сброс каждый кадр | Один кадр | Display list, батчи, временные массивы layout |
| Scratch | Thread-local арены с scoped-маркерами | Внутри функции | Буферы shaping, сортировки |

Данные переменной длины у виджетов (строки, массивы детей) живут в аллокаторе контекста с small-buffer оптимизацией.

### 3.4 Интерфейс аллокатора и правила

- Интерфейс из трёх операций (выделить, перевыделить, освободить) + userdata. Размер и выравнивание передаются явно, в том числе при освобождении: так допустимы простые и быстрые пользовательские аллокаторы.
- Аллокатор задаётся при создании контекста. Вне `base` и `platform` прямые вызовы `malloc/free` запрещены (проверяет линтер).
- Общие данные ресурсов неизменяемы после создания; счётчик ссылок атомарный, поэтому ресурсы можно безопасно передавать между потоками.

### 3.5 Нулевые аллокации в установившемся режиме

- Жёсткий gate: кадр без структурных изменений делает 0 вызовов аллокатора (тест со счётным аллокатором).
- Контейнеры резервируют ёмкость заранее, рост идёт по явной политике.
- Короткие строки хранятся inline; идентификаторы и ключи тем интернируются.
- Арены запоминают «высокую воду» и сжимаются после серии простых кадров, чтобы RSS не оставался раздутым после пика.

### 3.6 Безопасность

- Debug-аллокатор: канарейки, заливка освобождённой памяти, карантин, обнаружение double free, учёт по тегам и месту вызова.
- Арены в debug после сброса заливаются маркером и имеют «эпоху»: обращение к данным прошлого кадра ловится.
- Арифметика размеров идёт через функции с проверкой переполнения.
- Failure injection: тесты, где n-я аллокация возвращает ошибку, проверяют пути нехватки памяти на отсутствие утечек и падений.
- CI: ASan, UBSan, TSan, MSan (clang/Linux), Valgrind на Linux, Application Verifier/PageHeap на Windows, `leaks` на macOS; фаззинг парсеров и декодеров.
- Политика OOM: функции создания возвращают код ошибки; внутри кадра нехватка памяти приводит к пропуску кадра с сообщением, а не к падению; режим abort включается явно.

### 3.7 Учёт и бюджеты

Каждая аллокация несёт тег подсистемы; публичный API отдаёт статистику. У glyph-атласов, кэша изображений и кэша раскладки текста есть бюджеты в байтах и LRU-вытеснение. GPU-память учитывается отдельно. Предварительные цели (гипотезы для калибровки): порядка 300 байт ядра на виджет без специфичного состояния; 0 аллокаций в стабильном кадре.

### 3.8 Последствия

- Плюсы: предсказуемость, малая фрагментация, дешёвая диагностика, готовность к встраиванию.
- Минусы: каждая новая структура требует решения о классе времени жизни; ошибки в арене (ссылка пережила сброс) возможны, поэтому debug-проверки эпох обязательны.
- Любое будущее изменение классов или интерфейса аллокатора — архитектурное, через ADR.

## 4. Событийная система

### 4.1 Требования

Минимальная задержка от ввода до пикселей; нулевая нагрузка в простое; детерминизм порядка; безопасность при изменении дерева внутри обработчиков; расширяемость типов событий; возможность подавать синтетические события в тестах.

### 4.2 Поток события

1. **PAL** принимает сообщение ОС и нормализует его в событие фиксированного формата: тип, окно, монотонная метка времени ОС, модификаторы, идентификатор устройства, полезная нагрузка.
2. **Очередь контекста** (кольцевой буфер или чанки в арене). Коалесцирование: из серии движений мыши, прокруток и ресайзов остаётся последнее или суммарное событие.
3. **Input System** превращает сырой ввод в логический: клавиатура (физический скан-код, логическая клавиша, введённый текст как отдельные каналы), указатели (мышь, касание и перо — единая модель pointer с id), жесты (click, double click, long press, порог drag), фокус, захват указателя, горячие клавиши.
4. **Маршрутизация по дереву:** hit-test даёт путь от корня до цели; события проходят фазы capture, target, bubble; обработчик может пометить событие обработанным. Дефолтное действие выполняется, если событие не обработано.
5. **Уровень приложения:** простые callback-и (функция + userdata) и слой команд.

### 4.3 Модель диспетчеризации (альтернативы)

| Модель | Плюсы | Минусы |
| --- | --- | --- |
| Плоские callback-и на виджет (стиль Win32/GTK 1) | Просто | Нет единой маршрутизации; вложенные элементы координируются вручную |
| Capture/target/bubble (как в DOM) | Привычная и мощная модель вложенности; контейнеры могут перехватывать ввод (scroll, DnD, закрытие popup) | Чуть сложнее; нужны чёткие правила остановки |
| Сигналы и слоты (Qt, GObject) | Слабая связность кода приложения | Динамическая диспетчеризация и аллокации в C дороги |
| Message passing (Elm/MVU) | Чёткие потоки данных | Нужна система сообщений приложения; лишняя прослойка для виджетов |

**Решение:** DOM-подобная маршрутизация внутри ядра; в публичном API — callback-и. Для меню, горячих клавиш и кнопок — тонкий слой команд: идентификатор, состояние (доступна, отмечена), назначенные ускорители. Message passing можно строить поверх, ядро этого не требует.

### 4.4 Цикл событий и пробуждения

- **Блокирующее ожидание вместо опроса.** Windows: `MsgWaitForMultipleObjectsEx`; Linux: `poll`/`epoll` по fd (сокеты Wayland/X11, `eventfd` для пробуждения, `timerfd`); macOS: run loop приложения (источники и таймеры CFRunLoop). В простое поток спит и не просыпается без причины.
- **Потокобезопасный `mg_post`:** lock-free очередь MPSC плюс платформенное пробуждение (`SetEvent`/`PostMessage`, запись в `eventfd`, сигнал источника CFRunLoop).
- **Таймеры:** общая куча дедлайнов на монотонных часах; в ОС заводится один таймер на ближайший дедлайн.
- **Планировщик кадров:** кадр создаётся только при наличии damage или активных анимаций и синхронизируется с vsync (DXGI waitable swap chain/DwmFlush; CVDisplayLink/CADisplayLink; frame callback Wayland; Present/swap interval на X11).
- **Владение циклом:** основной режим — цикл принадлежит библиотеке; для интеграции в чужой цикл предусмотрен режим «внешней прокачки» с ограничениями. Модальные циклы ОС (изменение размера, перетаскивание, меню на Windows и macOS) перехватывают управление, поэтому рендер при live resize запускается от платформенных таймеров или display link.

Альтернатива — игровой цикл с постоянным опросом: проще, но противоречит цели нулевого CPU в простое. Отклонена.

### 4.5 Реентрантность и безопасность

- Уничтожение виджета в его же обработчике: объект помечается, handle сразу становится недействительным (поколение увеличивается), а память освобождается после завершения диспетчеризации текущего события.
- Путь события фиксируется снимком handles в scratch-арене; перед каждым вызовом handle проверяется на актуальность. Изменения дерева во время маршрутизации не ломают проход.
- Вложенные циклы допустимы только явно (модальные диалоги) и с ограничением глубины.
- Порядок: FIFO внутри источника; ввод обрабатывается раньше таймеров и анимаций; на итерацию цикла действует бюджет, чтобы шквал событий не заморозил отрисовку.
- Обработчики не бросают исключений и не используют `longjmp` через границы библиотеки.

### 4.6 Каталог событий

Окно (создание, закрытие, размер, перемещение, фокус, смена DPI, перекрытие, смена темы ОС), указатель (down, up, move, enter, leave, колесо, жесты), клавиатура (down, up, repeat), текстовый ввод (commit, composition start/update/end), фокус, drag-and-drop (enter, over, leave, drop), таймер, пользовательские события (зарегистрированный тип; небольшая нагрузка inline или указатель в арену), запросы accessibility, изменение буфера обмена, изменение системных настроек (тёмная тема, уменьшение анимации, локаль).

### 4.7 Измеримость и тестирование

- Метка времени ОС каждого события позволяет считать задержку от события до показа кадра (счётчик event-to-present).
- Платформа `null` и API инъекции синтетических событий; запись и воспроизведение сессий ввода для регрессий; фаззинг последовательностей ввода; отдельные тесты на «destroy во время callback» и вложенные изменения дерева.

### 4.8 Последствия

Фазы capture и bubble вместе с отложенным удалением увеличивают сложность ядра, но снимают целый класс ошибок. Обратная сторона: правила реентрантности нужно документировать для авторов пользовательских виджетов.

## 5. Архитектура Layout Engine

### 5.1 Требования

Стоимость пропорциональна изменённой части дерева; детерминизм; выразительность (flex, grid, dock, scroll, overlay); RTL и DPI с первого дня; виртуализация; интеграция с измерением текста; независимое тестирование.

### 5.2 Альтернативы (D-07)

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| Решатель ограничений (Cassowary, Auto Layout) | Максимальная выразительность | Стоимость растёт нелинейно; трудная отладка; неочевидные результаты при конфликтах; плохо сочетается с виртуализацией |
| Полный CSS (flexbox + grid + block/inline, как в Yoga, Taffy, браузерах) | Знакомая модель; готовые спецификации и тесты | Огромная спецификация, многое не нужно (float, margin collapsing, inline formatting); Yoga на C++, Taffy на Rust |
| Constraints вниз, размеры вверх (Flutter) | Один проход O(n); легко кэшировать; естественно для виртуализации | Intrinsic-размеры требуют отдельных запросов |
| Measure/Arrange (WPF) | Привычная двухфазная модель | Риск экспоненциального пере-измерения при вложенности без кэша |
| Ручное позиционирование | Предельно просто | Не масштабируется; нет адаптации к DPI, тексту и локали |

**Решение:** двухфазная раскладка Measure/Arrange с constraints (идеи Flutter и WPF). Measure получает constraints (мин/макс ширины и высоты) и возвращает размер; Arrange назначает дочернему узлу прямоугольник. Реализуемые контейнеры:

- **Stack** (горизонтальный и вертикальный): gap, align, justify, flex grow/shrink/basis — подмножество flexbox;
- **Wrap**;
- **Grid:** треки fixed, auto, fr, min/max; span; группы общего размера (shared size) для выравнивания несмежных элементов — это наша замена решателю ограничений;
- **Dock**, **Overlay/Anchor** (позиционирование popup относительно якоря), **Scroll** (viewport + content), **Virtual** (см. 5.5);
- **Custom** — пользовательские контейнеры через ту же vtable.

Не реализуем: float, margin collapsing, inline-контекст, селекторную систему позиционирования.

### 5.3 Инкрементальность и кэши

- Dirty-биты: нужно измерить, нужно разместить, у потомков есть работа. Инвалидация поднимается только до **relayout boundary** (узел с фиксированным размером по обеим осям или явно помеченный).
- **Кэш измерений:** на узле хранятся 1–2 последние пары «constraints → размер». Совпадение constraints и чистое поддерево дают O(1) и защищают от экспоненциального роста при вложенных flex.
- **Кэш размеров текста** живёт в Text Engine с ключом: строка (хэш), шрифт, доступная ширина.
- Координаты — float в логических пикселях (DIP). Привязка к физическим пикселям выполняется на Arrange для границ и baseline текста, чтобы линии оставались чёткими при дробном масштабе.
- Ожидаемая сложность: полный проход O(n); инкрементальный — O(размер поддерева от границы).

### 5.4 Локализация и DPI

Logical properties (start/end вместо left/right) и направление LTR/RTL на уровне окна или контейнера; единицы — DIP; размеры из метрик шрифта; min-content и max-content для текста; выравнивание по baseline. Это заложено в модель сразу, потому что поздний перевод на RTL ломает все контейнеры.

### 5.5 Виртуализация (списки, таблицы, деревья)

- Модель данных сообщает количество элементов; провайдер размеров бывает трёх видов: фиксированный (O(1)), известный переменный (префиксные суммы или дерево Фенвика, O(log n)), оценочный с ленивым измерением и коррекцией scroll anchor.
- Реализуются только видимые элементы и overscan; виджеты ячеек переиспользуются по типам ячеек. Выделение и фокус живут в модели, а не в виджетах, поэтому переживают уход ячейки из окна.
- Таблица: ширины столбцов, закреплённый заголовок, виртуализация по строкам (опционально по столбцам). Дерево: плоский индекс видимых узлов (состояние раскрытия + счётчики поддеревьев) поверх того же механизма списка.
- Цель: память и время кадра зависят от размера окна просмотра, а не от N.

### 5.6 Тестирование

Layout работает с интерфейсом узла (получить детей, measure, arrange, стили), поэтому тестируется на фейковых узлах без окон и шрифтов. Property-тесты проверяют инварианты: инкрементальный результат равен полному; результат не зависит от порядка инвалидаций; повторная раскладка идемпотентна.

### 5.7 Последствия

- Отказ от решателя ограничений ограничивает «экзотические» макеты; их покрывают Grid с общими размерами и пользовательские контейнеры.
- Измерение текста — самая дорогая часть раскладки, её производительность определяется кэшем Text Engine.
- API пользовательских контейнеров становится частью публичного контракта, его изменения — через ADR.

## 6. Архитектура Widget Engine

### 6.1 Требования

Единая объектная модель для встроенных и пользовательских виджетов; малый расход памяти на виджет; семантика для accessibility; тематизация; независимая тестируемость; удобный API.

### 6.2 Объектная модель (D-08)

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| Один универсальный узел с тегом типа и `switch` | Просто и компактно | Система закрыта: пользователь не добавит свой виджет; разрастающиеся `switch` |
| Базовая структура + таблица класса (vtable), наследование встраиванием | Открытая расширяемость; вызов за O(1); привычный для C приём | Нужна дисциплина встраивания; диспетчеризация вручную |
| Entity-Component-System | Кэш-эффективность, гибкая композиция | Нетипично для UI; иерархия и порядок рисования неочевидны; сложный API |
| Динамические объекты со словарями свойств | Гибкость, привязки | Аллокации, медленно, нет типобезопасности |

**Решение:** базовая структура виджета + таблица класса с цепочкой наследования. При регистрации класса его таблица «разглаживается» (унаследованные указатели копируются), поэтому вызов метода не обходит цепочку. Пользовательские виджеты создаются тем же механизмом, что и встроенные.

**Содержимое базы:** родитель и массив детей; флаги состояния (наведён, нажат, в фокусе, отключён, видим); dirty-биты (стиль, раскладка, рисование, accessibility); компактные layout-свойства и результат (прямоугольник); ссылка на класс и на разрешённый стиль; идентификатор; семантика a11y (роль, имя, состояние, значение); пользовательские данные с деструктором.

**Методы класса:** создание и уничтожение, measure, arrange, paint, обработка события, hit-test (необязательно), смена состояния, описание для accessibility, политика допустимых детей.

**Хранение детей:** сравниваем интрузивный связный список (дешёвая вставка, обход с промахами кэша) и непрерывный массив указателей (локальность при обходе layout и paint, обратный обход для hit-test, доступ по индексу, но вставка за O(n)). Берём массив; фаза 2 содержит замер, и при расхождении ADR пересматривается.

### 6.3 Композиция против монолита

Примитивы реализуют поведение: Box (фон, рамка, тень, clip), Label, Image, Canvas, Scroll, ядро редактирования текста, контейнеры. Композиты собираются из примитивов и темы: Button = Box + Label + необязательный Icon; Checkbox = Box-индикатор + Label. Выигрыш: меньше кода и единая стилизация. Цена: вложенные узлы увеличивают память на элемент. Для массовых элементов (ячейки таблиц, строки списков) допускаются оптимизированные монолитные классы без вложенных узлов; решение принимается по замерам.

### 6.4 Внешний вид: части и состояния

Виджет описывает части (у Slider: дорожка, заполнение, ползунок) и состояния (наведён, нажат, в фокусе, отключён, отмечен). Тема сопоставляет «класс, часть, набор состояний» со стилем (цвета, рамки, радиусы, тени, шрифт, отступы, переходы). Стиль разрешается лениво и кэшируется в узле; сбрасывается при смене состояния или темы. Альтернатива — жёстко зашитая отрисовка в виджете — отклонена: она делает темы и тёмный режим невозможными без правки кода.

### 6.5 Данные и построение дерева

- Любое изменение — через сеттер, который выставляет dirty-бит (операция идемпотентна, планировщик объединяет изменения).
- Для коллекций вводится интерфейс **модели данных**: количество, значение по индексу, сигналы вставки, удаления, перемещения, изменения и сброса.
- Автоматического data binding в ядре нет (он требует рефлексии). Необязательный слой привязок можно добавить позже.
- Построение дерева: функции создания принимают родителя и дескриптор; составные литералы C99 делают код читаемым. Декларативная разметка с hot reload — отдельный необязательный слой, вне ядра.

### 6.6 Popup, overlay и меню

Меню, выпадающие списки, контекстные меню и tooltips образуют popup-слой. Варианты: **overlay внутри окна** (дёшево, единый рендер, но обрезается границей окна) и **нативное popup-окно** (выходит за границы окна, нужно для меню у края и выпадающих списков). Решение: popup — лёгкое окно PAL со своей поверхностью (Wayland — `xdg_popup`, X11 — override-redirect с EWMH-типом, Windows — `WS_POPUP` без активации, macOS — безрамочная панель). Tooltips по умолчанию — overlay, если помещаются. Правила закрытия (клик вне, Esc, потеря фокуса), цепочки вложенных меню и захват указателя реализуются один раз.

Меню описываются моделью (команды, подменю, разделители, ускорители). На macOS обязательна нативная строка меню (`NSMenu`); на Windows и Linux меню рисуются нами: единый вид, темы, экспозиция в UIA и AT-SPI. Альтернатива — нативные `HMENU` на Windows: меньше кода, но нет темизации и тёмного режима (вопрос Q6).

### 6.7 Каталог виджетов и риски

| Виджет | Тип | Состав | Особенности и риск |
| --- | --- | --- | --- |
| Button | композит | Box + Label + Icon | Низкий |
| Checkbox, Radio | композит | Box + Label | Группы radio, tri-state |
| Slider | композит | Box ×3 | Drag, клавиатура, значение для a11y |
| Dropdown | композит | Button + popup-список | Popup, type-ahead |
| Tabs | композит | Ряд Button + контейнер | Переполнение, переупорядочивание |
| Text input | примитив + композит | Ядро редактирования | Высокий: IME, selection, undo, a11y |
| Scroll view | примитив | Viewport + полосы | Инерция, вложенные прокрутки |
| Menus, Context menus | композит + popup | Модель меню | Высокий: нативные требования |
| Tables, Tree views | композит | Virtual + модель | Высокий: виртуализация, редактирование ячеек |
| Dialogs | окно/overlay | Модальность | Фокус-ловушка, модальные циклы |
| Tooltips | overlay | Label | Таймеры, позиционирование |
| Panels, Docking | композит | Дерево докинга | Высокий, особенно на Wayland |
| Canvas, Image | примитив | Display list | Средний |

**Docking.** Отдельное дерево (split, tabs, floating) с сериализацией раскладки; панели — обычные виджеты. Перетаскивание вкладки наружу создаёт окно, а Wayland ограничивает позиционирование окон программой, поэтому floating-режим реализуется после split и tabs внутри окна.

**Drag & Drop.** Единый API с типизированной нагрузкой. Внешний DnD идёт через PAL (OLE, XDND, `wl_data_device`, `NSDragging`), внутренний использует тот же API с коротким путём. Drag image рисуется нами.

**Canvas.** Виджет с immediate-API, который пишет в тот же display list; позже — хуки встраивания GPU-текстуры или нативной поверхности.

### 6.8 Последствия

Стабильность API классов виджетов становится публичным контрактом: любое изменение таблицы класса — через ADR и политику deprecation. Взамен пользователи получают возможность строить собственные виджеты на тех же правах, что и встроенные.

## 7. Архитектура Text Engine

### 7.1 Назначение и слои

Подсистема превращает Unicode-текст и стили в позиционированные глифы, измеряет их, выдаёт hit-test, каретку и выделение, редактирует и растеризует. Это самая рискованная часть проекта. Слои:

1. **Шрифты:** загрузка файлов (TTF, OTF, TTC, variable), семейства и стили, метрики, перечисление системных шрифтов и цепочки fallback через PAL.
2. **Itemization:** разбиение на фрагменты по письменности, направлению (bidi), шрифту и стилю.
3. **Shaping:** кодовые точки в глифы и кластеры (лигатуры, кернинг, сложные письменности).
4. **Разбиение на строки:** правила UAX #14, ширина, многоточие.
5. **Раскладка:** параграфы, строки, выравнивание (start, end, center, justify), межстрочный интервал, baseline.
6. **Hit-test и каретка:** точка ↔ индекс, геометрия каретки и выделения с учётом bidi, навигация по графемам и словам (UAX #29).
7. **Растеризация и кэши.**
8. **Редактирование:** буфер, selection, undo/redo, IME, clipboard.

### 7.2 Выбор стека (D-09)

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| A. Нативные стеки (DirectWrite, CoreText, Pango + Fontconfig) | Лучший fallback и эмодзи; поддержка новых письменностей силами ОС | Три реализации; метрики и переносы расходятся между ОС, раскладка различается, golden-тесты невоспроизводимы; Pango тянет GLib, Cairo и HarfBuzz |
| B. Переносимый: FreeType + HarfBuzz + SheenBidi + libunibreak (+ собственные таблицы Unicode) | Один код на всех ОС; детерминизм и тестируемость; контроль над кэшами и растеризацией | Больше интеграции; перечисление системных шрифтов и fallback всё равно нужны от PAL; вид отличается от нативного (хинтинг, сглаживание) |
| C. Гибрид: интерфейс провайдера shaping/растеризации, по умолчанию B, нативные провайдеры позже | Путь к нативному качеству без переписывания верхних слоёв | Цена абстракции; риск расхождений между провайдерами |
| D. Минимальный: stb\_truetype + собственный shaping для латиницы | Мало кода и зависимостей | Нет сложных письменностей, bidi, цветных шрифтов; потом полная переделка |

**Решение:** вариант C, стартуем с B. Раскладка, редактирование и кэши работают с интерфейсом провайдера; первая реализация — B. Нативные провайдеры подключаем только при подтверждённой замерами необходимости. Здесь корректность и воспроизводимость поставлены выше нативности вида.

**Замечание о HarfBuzz.** Его код написан на C++ при C-совместимом API и собирается без C++ runtime (с отключёнными исключениями и RTTI). Допустимость такой зависимости сборки при отсутствии C++ в нашем коде и публичном API — вопрос Q4. Альтернативы: собственный shaper только для простых письменностей (высокий риск) или вариант A.

### 7.3 Растеризация и кэш глифов

- Глифы растеризуются через FreeType в A8, цветные (COLR, CBDT, sbix) — в RGBA. Хинтинг по умолчанию лёгкий; на HiDPI — выключен; переключается опцией.
- Позиционирование: по горизонтали с шагом 1/4 пикселя (до 4 вариантов глифа на малых размерах), по вертикали — привязка baseline к пикселю.
- Сглаживание: оттенки серого по умолчанию. LCD-режим — опция на Windows и Linux позже: он плохо дружит с GPU-смешиванием на прозрачных слоях, а macOS от него отказалась.
- SDF/MSDF-атлас хорошо масштабируется и дёшев при анимации размера, но хуже читается на малых кеглях; применяем опционально для крупного и анимируемого текста. Очень крупные глифы рисуются как контуры.
- Атлас: страницы A8 и RGBA, упаковка shelf или skyline, ключ (шрифт, glyph id, физический размер, субпиксельный сдвиг, флаги), LRU по страницам, бюджет памяти.
- Кэш раскладки параграфов: ключ (хэш текста, стиль, ширина, флаги), LRU; при редактировании пересчитывается только изменённый параграф.

### 7.4 Редактирование

| Структура буфера | Плюсы | Минусы |
| --- | --- | --- |
| Gap buffer | Просто и быстро для локальных правок | Дорогие прыжки по большому файлу; undo реализуется отдельно |
| Piece table | Дешёвый undo/redo; большие файлы | Индексация сложнее |
| Rope / B-tree | O(log n) на всё; очень большие документы | Самая сложная реализация |

**Решение:** интерфейс буфера; на старте gap buffer для однострочных полей и средних документов, piece tree добавляется, когда понадобятся документы в единицы мегабайт. Замена не затрагивает виджет. Остальное: undo/redo как журнал команд с группировкой; selection по графемным кластерам; слова по UAX #29; bidi-навигация; IME-композиция как отдельный слой над буфером; clipboard в UTF-8; для больших документов — раскладка только видимых строк с кэшем высот. Rich text (диапазоны атрибутов: шрифт, цвет, подчёркивание, ссылки) проектируем сейчас, реализуем поздно; полноценный HTML или Markdown-рендер вне объёма.

### 7.5 Интернационализация и платформа

- UTF-8 везде; некорректные последовательности заменяются на U+FFFD на границе API.
- Системный fallback даёт PAL: `IDWriteFontFallback` (Windows), `CTFontCreateForString` (macOS), Fontconfig (Linux); решения кэшируются.
- Цветные эмодзи: Segoe UI Emoji (COLR), Apple Color Emoji (sbix), Noto Color Emoji (CBDT или COLRv1) — требование к растеризатору.
- Variable fonts и OpenType-фичи входят в стиль; язык текста передаётся в shaping.
- ICU не включаем; решение пересматривается, если понадобятся collation и форматирование чисел и дат.
- Accessibility: текст, выделение и границы символов экспонируются через UIA Text, NSAccessibility и AT-SPI Text.

### 7.6 Последствия и ограничения объёма

Старт: латиница, кириллица, греческий, LTR, затем bidi и сложные письменности (арабский, деванагари, тайский, CJK) по тестовым корпусам. Вертикальный текст вне версии 1. Golden-тесты текста выполняются только с software backend и встроенными тестовыми шрифтами, иначе результат зависит от ОС. Трудоёмкость подсистемы закладывается в план отдельной фазой.

## 8. Архитектура рендеринга

Выбор backend и интерфейс «renderer core ↔ backend» описаны в разделе 2. Здесь — всё, что лежит выше: display list, damage, батчинг, HiDPI, software-путь, изображения.

### 8.1 Display list

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| A. Пересоздавать display list целиком каждый кадр | Просто; нет устаревших данных | Стоимость O(видимые виджеты) даже при крошечном изменении |
| B. Кэшировать записанные фрагменты на границах перерисовки (paint boundaries), перезаписывать только грязные | Стоимость O(грязное); основа для слоёв | Сложнее: инвалидация, порядок, смещения |
| C. Retained-граф сцены с GPU-слоями (композитор) | Лучшая анимация: прокрутка и трансформации без перерисовки | Много текстурной памяти; сложность; расхождение software и GPU |

**Решение:** в первой версии вариант A, но с отслеживанием грязных областей (для damage). Формат display list проектируется так, чтобы вариант B вводился без изменения контрактов: команды адресуются чанками, ресурсы — по handle. Переход к B и частично к C (слои для прокрутки и анимаций) решается по замерам отдельным ADR.

**Формат.** Линейный буфер POD-команд в арене кадра: push и pop clip (прямоугольник, скруглённый прямоугольник, контур), push и pop transform (2D-аффинное), push и pop слоя (opacity, режим смешивания), прямоугольник и скруглённый прямоугольник (заливка, рамка), линия, тень, изображение (с 9-slice), последовательность глифов, контур (заливка, штрих), пользовательская команда. Буфер сериализуется: это основа дампов, golden-тестов и отладки.

### 8.2 Damage tracking

Инвалидация виджета даёт объединение старых и новых границ в координатах окна (с учётом трансформаций, clip и теней). Окно хранит damage как небольшой набор прямоугольников (порядка 8–16) со слиянием по эвристике «площадь против числа областей». Software-путь перерисовывает только damage. GPU-путь использует scissor и частичный present, если backend сообщает поддержку (buffer age, dirty rects), иначе рисует кадр целиком, но только когда damage не пуст. Прокрутка в software: копирование уже нарисованного плюс перерисовка освободившейся полосы.

### 8.3 Батчинг, clip, слои

- Подряд идущие команды с одним пайплайном, текстурой и clip склеиваются; прямоугольники рисуются instanced (на инстанс: прямоугольник, цвета или градиент, радиусы, рамка, индекс clip).
- Порядок painter's algorithm сохраняется: команды не переставляются через пересечения. Переупорядочивание непересекающихся команд (проверка по AABB или тайловой карте) — возможная оптимизация, вводится только по замерам.
- Clip: выровненный по осям — scissor; скруглённый — данные в инстансе и SDF в шейдере (1–2 уровня вложенности); сложный контурный — маска (stencil или текстура).
- Offscreen-слои (группы с opacity, размытие, эффекты за прозрачным фоном) берутся из пула render-target. Эти эффекты дороги и включаются только по явному запросу.
- Цвет: float RGBA, **premultiplied alpha** везде. Смешивание по умолчанию в sRGB-пространстве (так ведут себя привычные UI и текст); линейное смешивание — опция Canvas. Wide gamut и HDR вне версии 1.

### 8.4 HiDPI и дробное масштабирование

Layout идёт в DIP, рендеринг — в физических пикселях; масштаб хранится на окне. При переносе окна между мониторами вызывается пересчёт раскладки и пересоздание зависящих от масштаба кэшей (глифы, растровые ресурсы). Windows: per-monitor DPI v2; macOS: `backingScaleFactor`; Wayland: `fractional-scale-v1` + `viewporter`; X11: масштаб из настроек и RandR. Иконки по умолчанию векторные (контуры), растровые — с вариантами @1x, @2x, @3x.

### 8.5 Software rendering

- **Растеризатор:** аналитическое сглаживание через накопление покрытия по scanline (подход signed-area), правила non-zero и even-odd; не MSAA. Быстрые пути для прямоугольников и скруглённых прямоугольников; глифы — копирование A8 с кэшем; линейные и радиальные градиенты; clip: прямоугольник + маска; смешивание: premultiplied source-over.
- **Оптимизации:** SIMD (SSE2/AVX2/NEON), тайловая многопоточность — только после замеров.
- **Вывод на экран:** Windows — DIB section и `BitBlt`; X11 — MIT-SHM; Wayland — буферы `wl_shm` с damage; macOS — `IOSurface` или `CGImage` в `CALayer`.
- **Роль:** эталон корректности для golden-тестов, fallback для RDP, VM и безопасного режима, режим работы CI. На 4K и частоте 120 Гц как основной режим не позиционируется.

### 8.6 Изображения

Декодирование (PNG, JPEG; WebP, GIF, SVG позже) выполняется на worker-потоках; результат — premultiplied RGBA. Малые изображения и иконки (примерно до 256×256) упаковываются в атласы, большие хранятся отдельными текстурами. Кэш с бюджетом и LRU; ленивая загрузка в GPU и освобождение. Качественный даунскейл (box/Lanczos) выполняется один раз при загрузке на CPU, билинейная фильтрация — на GPU.

### 8.7 Вывод кадра и многооконность

Каждое окно имеет собственную поверхность; device, атласы и кэши — общие. Задержка контролируется: waitable swap chain на Windows, ограничение числа drawable в Metal, swap interval в EGL. Невидимые и перекрытые окна не рендерятся. Живой ресайз обслуживается платформенным таймером или display link (см. 4.4).

### 8.8 Последствия

Два уровня (display list → батчи) дают прозрачную отладку и тестируемость: снимок display list воспроизводим без окна. Ценой оказывается дополнительный проход разрешения команд в батчи, который профилируется как отдельная стадия.

## 9. Стратегия поддержки Windows, Linux и macOS

### 9.1 Принципы

PAL — единственный слой, знающий про ОС. Интерфейс описывается возможностями, а различия поведения — флагами `caps` и документом «Platform Behavior Matrix». Есть платформа `null` для тестов. Публичный API не содержит платформенных типов; единственное исключение — явная функция получения нативного handle окна для интеграции, изолированная в отдельном заголовке.

### 9.2 Как реализовать PAL (D-10)

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| SDL3 или GLFW | Быстрый старт: окно и ввод на трёх ОС | Нет контроля над popup-окнами, нативными меню, деталями IME, DnD, accessibility, client-side decorations на Wayland и frame pacing; лишняя зависимость; ограничения вылезают поздно и дорого |
| Собственный PAL на нативных API | Полный контроль; точное соответствие требованиям; нет лишних зависимостей | Больше кода и поддержки; нужна экспертиза по трём платформам |
| Собственный PAL + SDL3 как временный dev-провайдер | Ускоряет фазу 1 | Второй провайдер надо поддерживать или выбросить; интерфейс PAL рискует «дрейфовать» под SDL |

**Решение:** собственный PAL; SDL3 в ядро не входит. Нужен ли SDL3 как временный провайдер для прототипа — вопрос Q5.

### 9.3 Что входит в интерфейс PAL

Жизненный цикл и цикл событий; окна (создание, размер, положение, состояния, декорации, popup, parent и модальность); мониторы и DPI; клавиатура и раскладки, указатель, касание, перо; IME; буфер обмена (текст, список URI, пользовательские типы); курсоры; DnD; таймеры и пробуждение; системные настройки (тёмная тема, акцентный цвет, уменьшение анимации, время двойного клика, локаль); диалоги ОС (файл, папка); шрифты ОС (перечисление, fallback); поверхности для рендеринга; хуки accessibility; время, потоки, мьютексы, атомики, TLS и `dlopen`.

### 9.4 Платформы

**Windows.** Win32 (`RegisterClassEx`, DWM, per-monitor DPI v2 через манифест); цикл на `MsgWaitForMultipleObjectsEx`; ввод через сообщения `WM_POINTER` (мышь, касание, перо); IME через TSF, начиная с IMM32 как первого шага; рендеринг D3D11 + DXGI flip model; accessibility — UI Automation (COM из C: многословно, но выполнимо); диалоги `IFileDialog`; буфер обмена и DnD — OLE. Риски: модальные циклы изменения размера, тёмный заголовок через атрибуты DWM, неполнота C11 в MSVC (см. 9.7).

**macOS.** AppKit. Objective-C допускается **только** внутри `src/platform/macos` (ARC включён) и backend Metal. Компоненты: `NSWindow` и `NSView`, `CAMetalLayer`, `CVDisplayLink` или `CADisplayLink`, `NSTextInputClient` для IME, `NSAccessibility`, `NSPasteboard`, `NSOpenPanel`, `NSMenu`. Решение об Objective-C — вопрос Q3: альтернатива — вызывать runtime через C API, но это хрупко, небезопасно по типам и тяжело сопровождается. Риски: приложение владеет run loop; модальные циклы меню и перетаскивания; полноэкранный режим и Spaces.

**Linux, Wayland.** `libwayland-client`, `xdg-shell`, `xdg-decoration` (GNOME не предоставляет серверные рамки, поэтому нужны **client-side decorations**: рисуем сами или через libdecor, решается ADR), `text-input-v3`, `fractional-scale-v1`, `viewporter`, `cursor-shape-v1`, `wl_data_device` (буфер обмена и DnD), `primary-selection`, `xkbcommon`, EGL (`wl_egl_window`) и `wl_shm`. Риски: фрагментация композиторов (GNOME, KDE, wlroots), отсутствие глобального позиционирования окон, зависимость IME и DnD от протоколов.

**Linux, X11.** `xcb` (+ xkb, xinput2, shm, randr, present, sync), EWMH и ICCCM, XDND, selections для буфера обмена, IME через XIM, IBus или fcitx (самое слабое место), GLX или EGL, `_NET_WM_SYNC_REQUEST` для плавного ресайза.

**Общее для Linux.** Все системные библиотеки (wayland-client, xkbcommon, xcb, EGL, D-Bus) загружаются через `dlopen`: один бинарник работает на разных конфигурациях и деградирует, а не падает. D-Bus нужен сразу трём функциям: порталам (`xdg-desktop-portal`: диалоги файлов, настройки темы), AT-SPI2 (accessibility) и IBus. Выбор клиента (libdbus-1 через `dlopen`, sd-bus или минимальная собственная реализация) — отдельный ADR.

### 9.5 Единое поведение

Одинаково на всех ОС: набор и семантика событий, модель фокуса и захвата, единицы DPI, порядок жизненного цикла окна. Нормализуется: ускорители (Cmd и Ctrl), направление прокрутки, расположение системных кнопок, поведение меню. Остаётся платформенным и документируется: нативная строка меню macOS, портал-диалоги Linux, рамки окна на Wayland.

### 9.6 Проверка

Платформа `null` + headless-рендеринг для юнит-тестов. Отдельное **conformance-приложение** с набором сценариев (окно, ресайз, DPI, IME, DnD, буфер обмена) выполняется на матрице окружений. CI: Windows (MSVC и clang-cl), Ubuntu (Xvfb для X11, headless Weston или sway для Wayland), macOS.

### 9.7 Компиляторы и стандарт

C17 на MSVC (2022+), clang и gcc; расширения компилятора не используются. Атомики, потоки и мьютексы подключаются через собственную тонкую обёртку (поверх C11 где доступно, поверх Interlocked, pthread, os\_unfair\_lock в остальных случаях), потому что поддержка C11-библиотек в MSVC неполна; VLA запрещены. `_Generic` допустим в публичных макросах (типобезопасные обёртки callback-ов).

### 9.8 Последствия

Собственный PAL — самая трудоёмкая часть «тонкого слоя», но он снимает риск ограничений сторонней абстракции в самых болезненных местах (popup, IME, DnD, accessibility). Objective-C на macOS — осознанное отступление от «только C»; оно изолировано одним каталогом и описано в зависимостях.

### 10.2 Правила

- Публичные заголовки живут только в `include/mygui/`; внутренние (`*_internal.h`) не устанавливаются и не видны потребителям.
- Каждая подсистема — отдельная CMake-цель `mygui::<имя>` со своими тестами; зависимости задаются только вниз по слоям (см. 1.3).
- Опции сборки: `MYGUI_BUILD_TESTS`, `MYGUI_BUILD_EXAMPLES`, `MYGUI_ENABLE_BACKEND_<NAME>`, `MYGUI_BUILD_SHARED`. Установка и экспорт для `find_package`.
- Предупреждения — ошибки в CI (`-Wall -Wextra -Wpedantic -Werror`, `/W4 /WX`), единый `warnings.cmake`. Форматирование — clang-format, статический анализ — clang-tidy.
- Файлы Objective-C (`.m`) допустимы только в `platform/macos` и `render/backends/metal`.
- Архитектурные решения фиксируются в `docs/adr/NNNN-название.md` по шаблону: контекст, решение, альтернативы, последствия, статус. Изменение контракта подсистемы без ADR запрещено.
- Процесс: trunk-based с короткими ветками; PR обязателен, содержит тесты и обновление документации; сообщения коммитов по Conventional Commits; релизы — теги и changelog.

### 10.3 Альтернативы

| Вариант | Оценка |
| --- | --- |
| Мультирепозиторий по подсистемам | Отклонён на раннем этапе: тяжёлая координация версий. Монорепозиторий с жёсткими границами CMake позволит выделить подсистемы позже |
| Системные пакеты вместо vendoring | Отклонён: нет воспроизводимости, проблемы на Windows и macOS |
| Git submodules для зависимостей | Допустим, но vendored-копия с контрольной суммой проще для воспроизводимых сборок и CI |

**Сознательно не используем:** Qt, GTK, Flutter и Skia, ICU (пока), GLib, Boost, SDL в ядре.

### 11.2 Политика зависимостей

1. Любая зависимость вводится через ADR: альтернативы, лицензия, размер, активность поддержки, история уязвимостей.
2. Хранится vendored: зафиксированная версия, контрольная сумма, файл лицензии, журнал локальных патчей.
3. Допустимы только разрешительные лицензии для статической линковки; LGPL и GPL в статической части запрещены.
4. Обёртка во внутреннем интерфейсе: код подсистем не вызывает стороннее API напрямую.
5. Необязательные зависимости отключаются опцией CMake.
6. Мониторинг уязвимостей и регулярное обновление; особый контроль для декодеров изображений и шрифтов (типичные цели атак). Ведётся SBOM.

## 14. Критерии производительности и методы измерения

### 14.1 Метрики и предварительные цели

Цели — гипотезы. На фазах 0–1 снимается baseline на эталонной матрице, после чего каждая цель калибруется и становится gate. «Жёсткий» gate строится на детерминированных счётчиках; «тренд» — на времени, подверженном шуму.

| Метрика | Как измеряем | Предварительная цель | Тип gate |
| --- | --- | --- | --- |
| Аллокации в стабильном кадре | Счётный аллокатор в тесте | 0 | Жёсткий |
| Пробуждения и CPU в простое | Счётчик итераций цикла + счётчики ОС (ETW, perf, Instruments) | 0 пробуждений за 60 с без анимаций | Жёсткий |
| Память ядра на виджет | Статистика аллокатора на сценах 1k, 10k, 100k | Порядка 300 байт базы | Жёсткий после калибровки |
| RSS пустого окна (software и GPU) | RSS и private bytes; отдельно наша куча и драйвер | Baseline; рост более 5% разбирается | Порог |
| Layout: полный и инкрементальный | Время и счётчик посещённых узлов, N = 1k, 10k, 100k | Инкрементальный пропорционален поддереву; полный на 10k узлов порядка 1–2 мс | Счётчик жёсткий, время — тренд |
| CPU-время кадра (наша часть) | Зоны профайлера, p50, p95, p99 | Сцена 1k виджетов порядка 1–2 мс | Тренд |
| Задержка ввод → показ | Метки ОС события до present; выборочно внешняя камера | Не более одного кадра сверх vsync | Тренд |
| Пропуски кадров | Скриптовая прокрутка 60 с на 60, 120, 144 Гц | Не более 0,1% | Тренд, ручной |
| GPU: draw calls, байты загрузки, overdraw | Счётчики renderer core, GPU-таймеры | Draw calls зависят от числа пайплайнов и текстур, а не от числа виджетов | Счётчик жёсткий |
| Кэш глифов | Доля попаданий | Не менее 99% в установившемся режиме | Счётчик |
| Текст | Пропускная способность shaping и раскладки; время до первой строки 1 МБ; задержка набора в документе 10 МБ | Калибруется | Тренд |
| Виртуализация | Прокрутка 1M строк; память и время кадра против N | Не зависят от N в пределах около 10% | Жёсткий (число живых виджетов не больше окна просмотра + overscan) |
| Время старта | До первого кадра, cold и warm | Калибруется | Тренд |
| Размер | Stripped static lib, hello-world, по backend | Бюджет после baseline | Порог |
| Утечки | Открытие и закрытие окон ×1000; виджеты ×1 000 000 | 0 байт | Жёсткий |

### 14.2 Методика

- **Харнесс `bench/`:** монотонные часы (QPC, `clock_gettime`, `mach_absolute_time`), прогрев, серия итераций, медиана и p95, p99, вывод в JSON; фиксация режима питания и частоты на эталонных машинах.
- **Встроенные счётчики кадра:** посещённые узлы layout, перерисованные виджеты, команды display list, draw calls, байты загрузки, промахи кэша глифов, аллокации, пробуждения. Детерминированные счётчики — основа жёстких gate: они не зависят от шума CI.
- **Встроенный профайлер:** зоны включаются флагом сборки, вывод в Chrome trace JSON; Tracy необязателен.
- **Внешние инструменты:** PIX и RenderDoc (GPU), Instruments (macOS), perf, callgrind и heaptrack (Linux), ETW/WPA и VMMap (Windows).
- **CI:** на общих раннерах время шумит, поэтому для него тренды; gate держатся на счётчиках и числе инструкций. Для регулярных замеров времени нужен выделенный раннер (вопрос Q10).
- **Эталонная матрица:** слабое (4 ГБ RAM, встроенный GPU, 60 Гц), среднее, мощное (144 Гц, дискретный GPU), Apple Silicon, Linux Mesa (Intel и AMD), масштаб 100%, 150%, 200%.
- **Сценарии:** пустое окно; 1k кнопок; 10k Label в ScrollView; Table на 1M строк; редактирование 1 МБ текста; 200 анимируемых элементов; шторм ресайзов; цикл окон ×1000; смена темы; смена DPI.
- **Сравнение:** для тезиса «лёгкий» заводим внутренние эталонные приложения на Qt, GTK и Dear ImGui с эквивалентным интерфейсом.
- **Корректность памяти:** ASan, UBSan, TSan, MSan, Valgrind, fail-nth injection и фаззинг; на каждый PR — быстрый набор, ночью — полный.

### 14.3 Правило оптимизации

Оптимизация принимается только с замером «до и после» на сценарии из `bench/`, со ссылкой на него в PR и, если меняется архитектура, в ADR (принцип 8).

Wayland и macOS-порт имеют статус «экспериментально», пока владелец не сможет их проверять.

### 16.4 Приоритет «лёгкости»

Цель владельца — приложения, лёгкие по размеру и по потреблению ресурсов. Следствия для проекта:

- **Метрики размера и памяти становятся блокирующими.** Размер статической библиотеки, размер hello-world exe, RSS пустого окна (отдельно для software и D3D11: драйвер GPU добавляет десятки мегабайт вне нашего контроля) и CPU в простое, равный нулю. Числовые бюджеты фиксируются после первого baseline и затем проверяются в CI.
- **Решение D-13: явная регистрация классов виджетов.** Каждый виджет живёт в отдельном объектном файле, а регистрация выполняется явным вызовом из кода приложения (без автоматической регистрации при старте). Тогда линкер выбрасывает неиспользуемые виджеты, и приложение платит размером только за то, чем пользуется.
- Остальное: линковка с удалением неиспользуемых секций, минимум зависимостей, необязательные модули под флагами сборки.

| --- | --- |
| A. DirectWrite на Windows | Рекомендую. Полноценный shaping для всех письменностей, поддерживаемых Windows (арабский, иврит, индийские, тайский, CJK), bidi, fallback шрифтов, цветные эмодзи, variable fonts, кернинг и лигатуры. Нет сторонних зависимостей, exe легче. Минус: привязка к Windows, компенсируется интерфейсом провайдера |
| B. Собственный shaper на C | Не рекомендую: арабский, индийские, тайский, кхмерский и бирманский — это годы работы с высоким риском ошибок |
| C. HarfBuzz и FreeType, встроенные в сборку | C++ в сборке; для Windows в v1 не нужен |

**Для других платформ** провайдер заменяется: на macOS — CoreText (это C API), на Linux — HarfBuzz и FreeType как системные библиотеки через `dlopen`. C++ при этом остаётся внутри системной библиотеки, а не в нашей сборке. Интерфейс провайдера из 7.2 это уже предусматривает.

**Последствия.** Внешний вид текста совпадает с системным. Тесты текста: раскладка (позиции глифов) проверяется точно, пиксели — с допуском, потому что растеризация DirectWrite зависит от версии системы. Риск: пригодность C-заголовков DirectWrite проверяется прототипом в фазе 2; если возникнут проблемы, пишем минимальные объявления интерфейсов вручную.

### 17.3 Простота разработки интерфейса

Принципы, которые становятся требованиями к публичному API:

1. Окно с кнопкой и текстом пишется примерно в 10–15 строк C без ручной настройки шрифтов, DPI и тем.
2. Разумные значения по умолчанию у всего: нулевой дескриптор даёт нормальный работающий виджет.
3. Дерево строится вложенными вызовами; раскладка по умолчанию — вертикальный stack с отступами. Всего четыре понятия: stack, grid, dock, scroll.
4. Единая форма обработчиков: функция + userdata для всех виджетов.
5. В debug-сборке понятные диагностические сообщения (какой виджет, что не так) вместо падений.
6. Красивая тема по умолчанию, светлая или тёмная в зависимости от системы.
7. Галерея примеров служит документацией: каждый виджет показан одним коротким примером.
8. «Тест простоты»: набор типовых окон (форма, список с поиском, настройки), которые должны укладываться в короткий код; размер кода примеров ведётся как метрика.

Позже, после v1: описание интерфейса в файле с hot reload и immediate-слой для отладочных панелей (удобен в игровом движке).

### 17.5 Статическая сборка: минусы

| Минус | Насколько существенен | Мера |
| --- | --- | --- |
| Каждое приложение несёт свою копию, код не разделяется между процессами | Мало: библиотека небольшая, и в exe попадает только используемое | — |
| Исправление в библиотеке требует пересборки каждого приложения | Для личных проектов приемлемо | Версионирование, скрипт пересборки |
| Плагин-DLL, использующий MoonGUI, получил бы вторую копию со своим состоянием | **Единственный существенный** | Глобального состояния нет (всё в `moon_context`): плагин получает таблицу функций хоста. DLL-сборку можно добавить при необходимости |
| Использование из других языков (Python, C#, Lua) удобнее с DLL | Сейчас не нужно | DLL-сборка и C-экспорт можно добавить позже |
| Линковка дольше, особенно с LTO | Мелочь | LTO только в release |

Плюсы: один exe без зависимостей, линкер выбрасывает неиспользуемое, нет проблем с версиями DLL, проще распространять. **Решение:** остаёмся при статической сборке.

### 17.6 Accessibility и сетевые API — разные вещи

- Accessibility — это интерфейс для экранных дикторов и других вспомогательных технологий, чтобы приложением могли пользоваться люди с нарушениями зрения. Он не связан с доступом к интернету.
- Подключение к API погоды — прикладная задача: HTTP-запрос из программы (WinHTTP или небольшая C-библиотека) и разбор JSON. В GUI это не входит, но всё нужное для удобной работы библиотека даёт: фоновые потоки, потокобезопасный `moon_post` для передачи результата в UI-поток, таймеры для периодического обновления.
- Если такие вещи понадобятся часто, их можно вынести в отдельный необязательный модуль (HTTP и JSON) в том же репозитории: он не войдёт в ядро и не увеличит размер приложений, которые его не используют. Решаем после v1.

### 18.4 Справка для ИИ (решение D-20)

Файл `docs/AI_REFERENCE.md` в репозитории. Его цель: любой новый чат с первой минуты пишет код под MoonGUI без догадок. Достаточно приложить файл или дать доступ к репозиторию. Содержание: назначение и правила проекта, соглашения (имена, владение, ошибки), как собирать и запускать, шпаргалка API по подсистемам, шаблоны типовых программ (окно, форма, список, Viewport, виджет рабочего стола), типичные ошибки и их диагностика.

Правила: справка обновляется в том же PR, в котором меняется API (это условие слияния); примеры из справки собираются в CI и поэтому не устаревают; на подсистему — не больше страницы.

### 18.5 Обновлённые критерии закрытия фазы

Фаза закрывается, когда: демо-приложение работает на вашем ПК; тесты и CI зелёные; метрики лёгкости не хуже предыдущего baseline или отклонение обосновано; справка для ИИ и документация обновлены; вы получили итоговый отчёт.
