# MoonGUI — мини-дизайн фазы 0 (фундамент)

*Редакция 1 · на утверждение · 4 ноября 2026 · исходный код не пишется до вашего одобрения*

## 0. Резюме

Фаза 0 создаёт основание проекта: репозиторий, сборку, автоматические проверки на Windows и Linux и библиотеку `base` (память, строки, контейнеры, логирование, потоки, время) с тестами и замерами. Окон и графики в этой фазе нет. Зато к её концу у нас будут: зелёная автоматическая проверка каждого изменения, строгие правила кода, память под контролем (тесты ловят утечки и повреждения) и первые числа размера и скорости, от которых мы будем считать «лёгкость».

**От вас в фазе 0:** утвердить этот дизайн (раздел 10), один раз скачать собранную программу замеров, запустить на своём ПК и прислать файл отчёта. Больше ничего технического.

Ссылки на разделы и решения (D-01…D-19, Q1–Q11) относятся к [архитектурной спецификации](https://claude.ai/artifact/UZqsntPutx2DTQp7569eFL).

## 1. Исходное состояние

Проверено через GitHub API (только чтение, ничего не менялось): репозиторий `TsomaStudio/EnterGUI` публичный, ветка `main`, один коммит «Initial commit», два файла: LICENSE (MIT) и README.md. Токен работает и даёт полные права на этот репозиторий.

Что сделаем: переименуем репозиторий в MoonGUI (старые адреса GitHub перенаправит сам), заменим лицензию на 0BSD (вы единственный автор, это допустимо) и напишем README. Так как репозиторий публичный, в нём не будет секретов: токен в файлы не попадает, а CI использует встроенный токен GitHub Actions.

## 2. Назначение и границы

**Зачем отдельная фаза.** Ошибки в работе с памятью, сборке и соглашениях дешевле исправить до появления GUI. Метрики лёгкости нужны с первого дня, иначе нам не с чем будет сравнивать.

**Входит:** репозиторий и процесс, система сборки, CI, библиотека `base`, тестовая и бенчмарк-инфраструктура, автоматические проверки архитектурных правил, первичная документация и справка для ИИ.

**Не входит:** окна, ввод, графика, текст, виджеты (фаза 1 и далее), сторонние библиотеки, оконные слои Linux и macOS.

**Принцип «по необходимости».** В `base` попадает только то, что потребуется в фазах 1–2. Остальное (приоритетная очередь, интернирование строк, small-string) откладывается до появления потребителя.

## 3. Архитектура фазы 0

### 3.1 Структура репозитория (подмножество 10.1 спецификации)

  docs/              architecture/, adr/, baselines/, coding-standard.md, AI_REFERENCE.md

### 3.2 Сборка (CMake)

- CMake 3.25+, генератор Ninja (Visual Studio тоже допускается). Язык C17, расширения компилятора выключены.
- Предупреждения: MSVC — `/W4 /WX /permissive- /utf-8 /Zc:preprocessor`; gcc и clang — `-Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wstrict-prototypes -Werror`. Единый `warnings.cmake` применяется ко всем нашим целям, к сторонним — нет.
- Пресеты: `win-msvc-{debug,release,asan}`, `linux-gcc-{debug,release}`, `linux-clang-{debug,release,asan-ubsan,tsan}`.
- Release: LTO, удаление неиспользуемых секций (`/Gy /OPT:REF /OPT:ICF`, `-ffunction-sections -Wl,--gc-sections`), скрытая видимость символов. На Windows статическая CRT (`/MT`) по умолчанию: меньше внешних зависимостей у готового exe.
- Цели: `moongui_base` (статическая библиотека), `moongui_tests`, `moongui_bench`. Опции: `MOONGUI_BUILD_TESTS`, `MOONGUI_BUILD_BENCH`, `MOONGUI_ENABLE_ASAN` и т.п. Тесты запускаются через CTest.
- Платформенные `#ifdef` допускаются только в `src/base/win32` и `src/base/posix`; остальное проверяет `check_layers`.

### 3.3 CI (GitHub Actions)

| Job | ОС и компилятор | Конфигурации | Назначение |
| --- | --- | --- | --- |
| win-msvc | Windows, MSVC | Debug, Release, Debug + ASan | Основная платформа |
| linux-gcc | Ubuntu, gcc | Debug, Release | Переносимость, предупреждения другого компилятора |
| linux-clang-san | Ubuntu, clang | ASan + UBSan; отдельно TSan | Память и потоки |
| checks | Ubuntu | — | clang-format, `check_layers`, `check_symbols`, самодостаточность заголовков |
| nightly | Ubuntu и Windows | Раз в сутки: расширенные прогоны, fail-nth, длинные model-тесты, Valgrind | Глубокие проверки |

Артефакты: Windows-программы (тесты и замеры) и отчёты размера. macOS-раннер добавится вместе с macOS-портом. Для публикации файлов `.github/workflows` токену нужно право Workflows; при отказе я скажу, какую галочку включить (раздел 6).

### 3.4 Процесс работы

- Ветки `phase0/<шаг>` → Pull Request → CI → слияние в `main`. Один PR соответствует одному этапу из раздела 9. Коммиты по Conventional Commits.
- В описании PR: что сделано, как проверено, что изменилось в документации, результаты замеров.
- После первого этапа в `main` напрямую ничего не пушится; `main` всегда зелёная.
- Каждый этап проходит ваш процесс: сборка, тесты, предупреждения, проверка памяти, обновление документации, итог.

### 3.5 Библиотека base: модули

| Модуль | Состав | Публичный? |
| --- | --- | --- |
| config и types | Фиксированные типы, макросы компилятора и платформы, макрос экспорта, версия | Да |
| assert и result | `MOON_ASSERT` (только debug), `MOON_CHECK` (всегда), перехватчик сбоев; коды результата `moon_result` с текстовым описанием | result — да; assert — внутренний |
| log | Уровни, приёмник-callback, форматирование без аллокаций в горячем пути, вырезание trace на этапе компиляции | Приёмник — да |
| memory | Интерфейс аллокатора; системный; считающий; отладочный (канарейки, заливка, карантин, отчёт об утечках); fail-nth для тестов; арена (линейная, метки, «высокая вода», «эпоха» в debug); scratch-арены (thread-local, scoped); пул и slotmap с generation-handles; арифметика размеров с проверкой переполнения | Интерфейс аллокатора — да; остальное внутреннее |
| str | `moon_str` (указатель + длина), UTF-8 (проверка, обход кодовых точек, кодирование), builder; преобразование UTF-8 ↔ UTF-16 для Windows | `moon_str` — да |
| containers | Динамический массив, hashmap (open addressing), кольцевой буфер, bitset. Обобщённые функции с размером элемента плюс типизированные макросы-обёртки (`_Generic` там, где помогает) | Внутренний |
| sys | Потоки, mutex, condvar, once, TLS; атомики над `<stdatomic.h>` (gcc, clang) и Interlocked (MSVC); монотонные часы, sleep, чтение файла целиком | Внутренний |
| stats | Реестр атомарных счётчиков и gauge, снимок на кадр или на тест; зоны профайлера (включаются флагом) с выводом в Chrome trace JSON | Внутренний (позже `moon_stats` станет публичным) |

Правила дизайна `base`: никакого глобального изменяемого состояния кроме thread-local scratch-арен; любая функция, которая может не получить память, возвращает код ошибки; у каждой аллокации есть явный класс времени жизни (3.3 спецификации); у каждой структуры с владением есть парная функция освобождения.

### 3.6 Тестовая инфраструктура

- **Собственный минимальный раннер** (порядка 300 строк C, только для тестов): макросы объявления тестов и проверок, автоматическая регистрация (в тестовом коде допустимы атрибут `constructor` и секция CRT для MSVC; в самой библиотеке автоматической регистрации нет, см. D-13), вывод в консоль и в JUnit XML для CI, таймаут на тест, фильтр по имени.
- **Контроль памяти в каждом тесте:** тест выполняется со считающим аллокатором, в конце проверяется баланс; любая утечка проваливает тест. Режим fail-nth: n-я аллокация отказывает, перебираются все n.
- **Перехват сбоев:** `MOON_ASSERT` и `MOON_CHECK` в тестах вызывают обработчик, превращающий сбой в проваленный тест (так проверяется, что debug-аллокатор ловит двойное освобождение и порчу границ). Проверки настоящих аварий выполняются в дочернем процессе.
- **Модельные тесты:** случайные последовательности операций над контейнерами и аллокаторами сравниваются с простой эталонной моделью; зерно генератора печатается при сбое.
- Готовые раннеры (Unity, utest.h, Criterion) отклонены: нужна тесная связь с аллокаторами, счётчиками и fail-nth, а свой раннер небольшой.

### 3.7 Бенчмарки и метрики лёгкости

- **Harness:** монотонные часы, прогрев, серия итераций, медиана, p95, p99, min, max; JSON с метаданными (коммит, компилятор, CPU, ОС, режим сборки).
- **Сценарии фазы 0:** микробенчмарки аллокаторов (системный, арена, пул), контейнеров, UTF-8, счётчиков; пустая программа (старт и RSS).
- **Метрики лёгкости (baseline):** размер `moongui_base` и hello-exe в release, время сборки, RSS пустой программы. `size_report.py` запускается в каждом CI-прогоне; результаты — в артефактах, baseline — в `docs/baselines/phase0.md`.
- **Ваш ПК:** из артефакта CI вы скачиваете `moongui_bench.exe`, запускаете одной командой и получаете `bench_report.json` (в нём же характеристики железа). Сравнение прогонов — `bench_compare.py`.
- Жёсткие gate пока только детерминированные (аллокации, байты, размеры); временные метрики — тренды.

### 3.8 Автоматические проверки архитектуры

- `check_layers.py` разбирает `#include` и граф CMake и запрещает: платформенные заголовки вне `src/base/{win32,posix}`, зависимости вверх по слоям, включение внутренних заголовков из публичных. У скрипта есть негативные тесты: заведомо нарушающий пример обязан провалиться.
- `check_symbols.py` проверяет, что все экспортируемые символы библиотеки начинаются с `moon_` или `MOON_` (`nm` на Linux, `dumpbin /symbols` на Windows). Это защита от конфликтов имён, урок `mg_`.
- Каждый публичный заголовок компилируется отдельно в строгом режиме C17.
- Форматирование проверяет clang-format; мягкое предупреждение при файле больше 1000 строк.

Публичная поверхность минимальна: добавить в API проще, чем убрать.

### 4.1 Публичные заголовки

| Заголовок | Содержимое |
| --- | --- |
| `moongui/config.h` | Версия (MAJOR, MINOR, PATCH), макрос экспорта `MOON_API`, минимальные определения платформы и компилятора, защита `extern "C"` |
| `moongui/types.h` | Целочисленные типы из `<stdint.h>`, `bool`, `moon_str` (указатель + длина), `moon_result` и функция текстового описания кода |
| `moongui/memory.h` | Интерфейс аллокатора (alloc, realloc, free + userdata; размер и выравнивание передаются явно) и системный аллокатор по умолчанию |
| `moongui/log.h` | Уровни, приёмник (callback + userdata), установка приёмника |

Всё остальное (арены, контейнеры, потоки, счётчики, assert) живёт во внутренних заголовках `src/base/` и наружу не выходит, пока не появится причина.

### 4.2 Соглашения (закрепляются в coding-standard)

1. **Имена:** функции `moon_<модуль>_<действие>`, типы `moon_<имя>` без суффикса `_t`, макросы и константы `MOON_<ИМЯ>`, значения перечислений `MOON_<ТИП>_<ЗНАЧЕНИЕ>`.
2. **Ошибки:** возврат `moon_result` (0 — успех), значения через выходные параметры; без `errno`, `setjmp` и исключений.
3. **Владение:** у каждой функции создания есть парная функция уничтожения; в документации указано `borrowed`, `owned` или `copied`. По умолчанию библиотека копирует переданные строки.
4. **Дескрипторы:** параметры создания объектов передаются структурой с полем `size` первым; нулевая инициализация даёт значения по умолчанию.
5. **Типы:** размеры — `size_t`, индексы и счётчики в публичном API — `uint32_t`, геометрия — `float`.
6. **Запрещено:** VLA, расширения компилятора; `goto` допустим только для единого выхода с очисткой.
7. **Защита от повторного включения:** классические `#ifndef MOON_<ПУТЬ>_H`.
8. **Язык:** идентификаторы и комментарии в коде — английский; документы проекта — русский (решение P1).
9. **Документация API:** каждая публичная функция имеет Doxygen-комментарий (назначение, параметры, владение, потокобезопасность, коды ошибок).

## 5. Зависимости

- **Библиотека:** ни одной сторонней. Используются только стандартная библиотека C и системные API (Win32, POSIX threads).
- **Для разработки:** CMake 3.25+, Ninja, Python 3 (скрипты проверок и сравнения бенчмарков; для сборки библиотеки не нужен), clang-format, компиляторы MSVC 2022, gcc 12+, clang 15+, санитайзеры, Valgrind (Linux, nightly).
- **На вашем ПК:** ничего устанавливать не нужно, готовые exe берутся из артефактов CI.

## 8. Критерии готовности (gate фазы 0)

1. Репозиторий MoonGUI: переименован, лицензия 0BSD, README, структура, шаблон ADR и записи D-01…D-19, coding standard, скелет AI\_REFERENCE.
2. CI зелёный на всех job из 3.3; nightly запущен вручную хотя бы раз.
3. Ноль предупреждений на строгих флагах на всех компиляторах.
4. Все тесты проходят под ASan и UBSan; потоковые под TSan; нулевой баланс аллокаций; fail-nth пройден для всех модулей с аллокациями.
5. `check_layers` и `check_symbols` работают в CI вместе с негативными тестами.
6. Benchmark-harness выдаёт JSON; baseline зафиксирован в `docs/baselines/phase0.md`: размеры библиотеки и hello-exe, время сборки, микробенчмарки.
7. Публичные заголовки на 100% покрыты Doxygen-комментариями; каждый компилируется отдельно.
8. Вы запустили бенчмарк на своём ПК и прислали `bench_report.json`.
9. Итоговый отчёт фазы: что сделано, замеры, список отложенного, предложения по фазе 1.

## 9. Этапы реализации
